# Дефекты SVD-описания К1921ВГ1Т и их исправление

[English version](SVD_FIXES.en.md)

Rust-PAC `k1921vg1t-pac` сгенерирован инструментом svd2rust из SVD-описания микроконтроллера
К1921ВГ1Т, входящего в SDK АО «НИИЭТ». Исходный файл svd2rust не принимает. В документе перечислены
все найденные дефекты: что исправлено, на каком основании и что оставлено без изменений.

## Исходные данные

| | |
|---|---|
| Исходный SVD | `tools/svd/K1921VG1T.svd` из [k1921vg1t_sdk](https://gitflic.ru/project/niiet/k1921vg1t_sdk), коммит `9fa40f85be5b` (14.07.2026), `<version>2.8</version>`, SHA-256 `56c48c5763a8948205322001c5e57b5ffa1b0655e537edd26d084e451553400c` |
| Исправленный SVD | [`K1921VG1T.patched.svd`](K1921VG1T.patched.svd), SHA-256 `5c2766591523ee45573ace3116dddfaa16edab9ca547856692ac2213acd40064` |

| Генератор | svd2rust 0.37.1, form 0.13.0, rustfmt 1.9.0 |
| Документация для сверки | «Руководство пользователя К1921ВГ1Т» (UM_K1921VG1T_10YA), далее — РП; страницы указаны по печатной нумерации |

SHA-256 исходного файла указан для файла, извлечённого командой `git show` (см. ниже). Копия в рабочем
каталоге SDK на Windows может иметь концы строк CRLF, и её контрольная сумма будет другой.

Номера строк ниже относятся к **исходному** файлу SDK.

Исправленный SVD получается из исходного так:

```sh
git -C k1921vg1t_sdk show 9fa40f85be5b:tools/svd/K1921VG1T.svd > K1921VG1T.svd
patch -o K1921VG1T.patched.svd K1921VG1T.svd < K1921VG1T.svd.diff
```

PAC генерируется так (каталог `src/` после этого совпадает с репозиторием побайтно):

```sh
svd2rust --target riscv -i K1921VG1T.patched.svd
form -i lib.rs -o src/ && rm lib.rs
rustfmt --edition 2021 --config newline_style=Unix src/lib.rs build.rs
```

Параметр `newline_style=Unix` нужен для воспроизводимости: без него на Windows rustfmt записывает
файлы с концами строк CRLF.

## Сводка

**Группа А — нарушения стандарта SVD и ошибки описания, из-за которых исходный файл не проходит
генерацию или даёт неверный код (8 классов, 48 мест).** Исключение — класс 8: стандарт такое описание
прямо не запрещает, правка нужна из-за схемы имён svd2rust. Для каждого класса проверено, что без его
исправления PAC не генерируется или не компилируется: откатывалась только правка этого класса,
остальные оставались. Внутри класса это верно не для каждого места: из восьми мест класса 4 генерацию
останавливает только одно (п. 4), а класс 7 становится блокирующим лишь после исправления размера
регистра `TMR0.CAPCOM[%s].Reserved` (п. 7).

| № | Дефект | Мест | Было | Стало | Что происходит без исправления |
|---|---|---|---|---|---|
| 1 | Недопустимое значение порядка байт | 1 | `Endian.LITTLE` | `little` | svd2rust: `Unknown endianness` |
| 2 | Пустой тег `nvicPrioBits` | 1 | `<nvicPrioBits />` | `<nvicPrioBits>4</nvicPrioBits>` | svd2rust: `Expected content in <nvicPrioBits> tag` |
| 3 | Регистры без имени | 30 | `<name />` | `<name>VALUE</name>` | svd2rust: `Expected a <name> tag` |
| 4 | Регистры нулевой ширины | 8 | `<size>0</size>` | `<size>32</size>` | svd2rust: `Reset value 0x10102 doesn't fit in 0 bits` |
| 5 | Символы `<>` в имени регистра | 2 | `<>TACC0`, `<>Reserved` | `TACC0`, `Reserved` | svd2rust аварийно завершается: `"<>tacc0" is not a valid Ident` |
| 6 | Регистр `write-only`, но у него есть читаемые поля | 4 | `write-only` | `read-write` | svd2rust: `Field ADC.SEQ[%s].SCVAL.RCNT is not writtable or readable` |
| 7 | Шаг массива `TMR0.CAPCOM` меньше размера элемента | 1 | `<dimIncrement>12</dimIncrement>` | `16` | svd2rust: `Cluster CAPCOM[%s] has size 128 bits that is more then array increment 96 bits` |
| 8 | Кластер `ADC.ACTL` и его регистр названы одинаково | 1 | регистр `ACTL` | `CTRL` | svd2rust проходит, rustc: ``error[E0072]: recursive type `adc::actl::Actl` has infinite size`` |

Сообщения приведены дословно, включая орфографию svd2rust (для класса 8 вместе с E0072 выдаётся
`error[E0428]: the name Actl is defined multiple times`). svd2rust останавливается на первой ошибке,
поэтому остальные места каждого класса найдены по файлу.

**Группа Б — дефекты, найденные проверкой исправленного SVD.** Генерации они не мешают. Найдены
сверкой SVD с РП и с заголовком `K1921VG1T.h` из того же SDK.

| № | Дефект | Решение |
|---|---|---|
| 9 | Размер `addressBlock` у WDT и TMR0 меньше, чем занимают их регистры | исправлено |
| 10 | В DAC0 описан регистр, которого нет в РП и в заголовке SDK | описано, не исправлялось |
| 11 | В SVD нет пяти источников прерываний из таблицы прерываний РП | 4 добавлены, 1 описан |
| 12 | Поля статуса HASH.SR помечены как `write-only` | описано, не исправлялось |
| 13 | TMR4–TMR15 унаследовали от TMR0 четыре блока CAPCOM, по РП у них один | описано, не исправлялось |
| 14 | Значения сброса HASH.SR и MSC.U_ITEM расходятся с РП | описано, не исправлялось |
| 15 | В перечислении поля CRYPTO.CONTROL.ALGORITHM нет значения «Магма» | исправлено |

**Группа В — следы примера ARM.** Шапка файла совпадает с шапкой примера `ARM_Example.svd` из
пакета CMSIS_5 компании ARM. Подробности ниже; правились только два поля.

Итого в `K1921VG1T.svd.diff`: 48 мест группы А, 7 правок группы Б (размеры двух блоков, четыре
прерывания и значение «Магма») и 2 поля метаданных группы В.

## Группа А — подробно

### 1. Порядок байт

- **Где:** строка 24, блок `<cpu>`.
- **Было / стало:** `<endian>Endian.LITTLE</endian>` → `<endian>little</endian>`.
- **Основание:** спецификация CMSIS-SVD (элемент `cpu`) допускает значения `little`, `big`,
  `selectable`, `other`. Значения `Endian.LITTLE` в списке нет.

### 2. Тег nvicPrioBits

- **Где:** строка 27, блок `<cpu>`.
- **Было / стало:** `<nvicPrioBits />` → `<nvicPrioBits>4</nvicPrioBits>`, на том же месте: перед
  `<vendorSystickConfig>`, как требует порядок элементов в схеме CMSIS-SVD.
- **Основание:** NVIC — контроллер прерываний ядер Cortex-M. В К1921ВГ1Т его нет, прерывания
  обслуживает PLIC. Тег относится к ядрам Cortex-M (в `ARM_Example.svd` он есть со значением 3), но
  спецификация CMSIS-SVD делает его обязательным внутри `<cpu>`, и svd2rust требует, чтобы он
  содержал число: без тега он выдаёт `Expected a <nvicPrioBits> tag, found none`, с пустым тегом —
  ошибку из таблицы выше. Значение 4 условное: в PAC оно попадает только в константу
  `NVIC_PRIO_BITS`, которую код крейта не использует.

### 3. Регистры без имени (30 мест)

- **Где:** строки 3880, 3909, 5320, 5652, 5702, 5731, 10703, 10746, 12207, 12259, 12288, 12317, 12642,
  17750, 18032, 20384, 23460, 23540, 23893, 23966, 24833, 25561, 26053, 26100, 27694, 27976, 34044,
  34073, 37076, 38114.
- **Было / стало:** `<name />` → `<name>VALUE</name>`.
- **Основание:** во всех 30 случаях это единственный регистр внутри кластера-массива, например
  `GPIOA.MASKLB[%s]`, `RCU.UARTCFG[%s]`, `ADC.CHDELAY[%s]`, `CRYPTO.KEY[%s]`, `MSC.U_ITEM[%s]`. Имя
  массиву даёт кластер, у регистра оно пустое. В CMSIS-SVD имя регистра обязательно. Имя `VALUE`
  выбрано в работе, в РП его нет. В PAC доступ выглядит так: `rcu.uartcfg(0).value()`. Такие регистры
  используются в примерах репозитория: через `rcu.uartcfg(0).value()` настраивается тактирование
  UART (`rust_uart`, `rust_adc`, `rust_crypto`, `rust_pll`), через `adc.chdelay(63).value()` —
  задержка канала АЦП (`rust_adc`).

### 4. Регистры нулевой ширины (8 мест)

- **Где:** строки 6232 (`CAN.Node[%s].Reserved`), 16217 (`DMA.CH[%s].Reserved`), 17560 (`DMA.Reserved`),
  21511 (`SIU.Reserved`), 25305 (`SRAM.Reserved`), 26456 (`SDRAM.Reserved`), 32374 (`DAC0.Reserved`),
  33719 (`TMR0.CAPCOM[%s].Reserved`).
- **Было / стало:** `<size>0</size>` → `<size>32</size>`.
- **Основание:** семь из восьми регистров — резервные слоты без полей и без описания, со значением
  сброса 0. У восьмого, `DAC0.Reserved`, есть поля до бита 16 и значение сброса `0x10102`, что с
  шириной 0 бит несовместимо; на нём svd2rust и останавливается. Остальные семь мест svd2rust
  принимает, но генерирует неверный код: тип регистров получается `u8`, а массив `CAN.Node[%s]` пропадает (поле
  `node: ()`). Проверено откатом этих семи правок. Всем восьми задана ширина 32 бита — размер
  регистров по умолчанию в этом файле. Адрес каждого регистра задан явно (`addressOffset`), поэтому
  исправление размера не сдвигает соседние регистры. Регистр `DAC0.Reserved` разобран отдельно в п. 10.

### 5. Символы `<>` в имени (2 места)

- **Где:** строки 10540 и 10683, кластер `ADC.ACTL[%s]`.
- **Было / стало:** `<>TACC0` → `TACC0`, `<>Reserved` → `Reserved`. В XML символы `<` и `>` записываются
  как `&lt;` и `&gt;`, поэтому в файле стоит `&lt;&gt;TACC0`, то есть имя буквально начинается с `<>`.
- **Основание:** имя регистра должно соответствовать типу `dimableIdentifierType` XSD-схемы
  CMSIS-SVD: допустимы латинские буквы, цифры, `_` и подстановка `%s`. Символы `<>` в нём недопустимы. Соседний регистр того же кластера называется `TACC1`,
  без префикса.

### 6. Регистр «только запись» с читаемыми полями (4 места)

- **Где:** строки 9926 (`ADC.SEQ[%s].SCVAL`), 12162 (`HASH.SR`), 21121 (`SIU.NODESTEST`),
  38118 (`MSC.U_ITEM[%s]`).
- **Было / стало:** у регистра `write-only` → `read-write`. Доступ полей не менялся.
- **Основание:** в каждом из четырёх регистров есть и поля только для чтения, и поля только для
  записи. Например, у SCVAL поле ICLR записываемое, а ICNT и RCNT читаемые. Поэтому регистру указан
  доступ `read-write`. Сверено с РП: SCVAL — с. 744 (на битовой диаграмме ICLR помечено «з»,
  ICNT и RCNT — «ч»), NODESTEST — с. 581 (биты статуса STEx/STCx и команды CLR/START), U_ITEM — с. 699
  (поле CLEAR сбрасывает бит VALID записью единицы, остальные поля отражают принятый кадр), HASH.SR —
  с. 787 (флаги BUSY и DMAS читаются, DCIS и DINIS выставляются аппаратно и сбрасываются, в частности,
  записью нуля; о доступе к самим полям DCIS и DINIS см. п. 12).

### 7. Шаг массива TMR0.CAPCOM

- **Где:** строка 33606.
- **Было / стало:** `<dimIncrement>12</dimIncrement>` → `16`.
- **Основание:** элемент массива — четыре 32-битных регистра (`CTRL`, `VAL0`, `VAL1`, `Reserved` на
  смещении `0xC`), то есть 16 байт. При шаге 12 соседние элементы перекрываются. По РП (с. 673)
  блоки начинаются с `+100h`, `+110h`, `+120h`, `+130h`, шаг 16 байт.
- **Замечание:** в исходном файле шаг 12 не противоречит нулевой ширине `CAPCOM[%s].Reserved` (п. 4):
  если откатить обе правки вместе, svd2rust и компилятор ошибок не выдают, а CAPCOM занимает
  `0x100–0x12F`. Значит, ошибку шага выявляет сверка с РП, а svd2rust — только после исправления
  ширины.

### 8. Кластер и регистр с одним именем

- **Где:** строка 10415.
- **Было / стало:** регистр `ACTL` внутри кластера `ACTL[%s]` переименован в `CTRL`. Описание регистра
  в SVD — «ADC module control register».
- **Основание:** в модуле `adc::actl` svd2rust объявляет и структуру кластера `Actl`, и тип регистра
  `Actl`. Имена совпадают (E0428), а поле `actl: Actl` внутри структуры ссылается на саму структуру
  (E0072). svd2rust этого не замечает, ошибки выдаёт компилятор. Спецификация CMSIS-SVD требует
  уникальности имён регистров и, отдельно, имён кластеров в пределах периферии; совпадение имени
  кластера с именем вложенного регистра она прямо не запрещает. Правка нужна из-за схемы имён
  svd2rust. В PAC доступ выглядит так: `adc.actl(3).ctrl()`.

## Группа Б — подробно

### 9. Размер addressBlock (исправлено)

- **WDT**, строка 24864: блок `0x1c` байт, но регистры `LOCK`/`LOCKSTAT` находятся на смещении `0xC00`
  (РП, с. 807: регистр блокировки сторожевого таймера LOCK, смещение +C00h). Стало `0xc04`.
- **TMR0**, строка 32850: блок `0x130` байт. Это ровно `0x100 + 4 × 12` и совпадает с неверным шагом
  CAPCOM из п. 7. С шагом 16 последний блок CAPCOM заканчивается на `0x140`. Стало `0x140`.
- На сгенерированный код не влияет: проверено повторной генерацией.

### 10. Регистр DAC0 по смещению 0x40 (не исправлялось)

- **Где:** строки 32369–32374 и далее.
- **Что:** в DAC0 описан регистр `Reserved` с описанием «MCP4921 control register» и полями `READY`,
  `BUF_VREF`, `NOT_GAIN`, `SCLK_DIV`. MCP4921 — 12-разрядный ЦАП с интерфейсом SPI производства
  Microchip, отдельная микросхема ([техническое описание DS22248A](https://ww1.microchip.com/downloads/en/DeviceDoc/22248a.pdf)).
  Описания двух из четырёх полей совпадают с описанием битов управляющего слова MCP4921 (DS22248A,
  с. 24, Register 5-1): поле `BUF_VREF` — «VREF Input Buffer Control: 1 - buffered…», в даташите бит `BUF` — «VREF Input
  Buffer Control bit»; поле `NOT_GAIN` — «1 - 1x … 0 - 2x», в даташите бит `GA` — «1 = 1x … 0 = 2x».
- **Сверка:** в РП последний регистр блока ЦАП — `TEST` по смещению `+28h` (с. 759). Регистра по
  смещению `+40h` и полей с такими именами в РП нет. В структуре `DAC_TypeDef` заголовка `K1921VG1T.h`
  его тоже нет. Регистр выходит и за `addressBlock` блока DAC0 (`0x40` байт). Блок DAC1 описан как
  производный от DAC0 (`derivedFrom`) и наследует этот регистр.
- **Решение:** регистр оставлен. Отсутствие в документации не доказывает, что регистра нет в
  кристалле. После правки 4 (ширина 0 → 32) он попал в PAC как `dac0.reserved()` (и `dac1.reserved()`).
  Пользоваться им не следует. Примеры репозитория к нему не обращаются.

### 11. Отсутствующие прерывания (4 добавлены, 1 описано)

- **Что:** таблица прерываний РП (табл. 13.1, с. 187–193) и перечисление `IsrVect_IRQ_*` в
  `K1921VG1T.h` содержат пять источников, которых нет в SVD (резервные номера 168 и 169, которые в
  таблице тоже есть, не считаются). Без них в PAC нет соответствующих вариантов `Interrupt` и имён
  обработчиков в `device.x`.
- **Добавлено** (номер и имя по РП, описание — из `K1921VG1T.h`):

  | Номер | Имя | Периферия в SVD |
  |---|---|---|
  | 4 | `FLASH` | `FLASHM` |
  | 164 | `USB0` | `USBCTR0` |
  | 165 | `USB1` | `USBCTR1` |
  | 219 | `PWMx_TZ` | `PWM0` (по РП — общее прерывание детекторов аварий блоков ШИМ) |

  В заголовке SDK последнее называется `PWMxTZ`, в РП — `PWMx_TZ`. Использовано имя из РП.
- **Не добавлено:** 6 `L2_ERROR` (ошибка кэша L2). Прерывание в SVD описывается внутри периферии, а
  периферии кэша L2 в SVD нет; привязывать его к другой периферии не стали.
- **Сверка после правки:** номера всех 251 прерывания SVD совпадают с `K1921VG1T.h` и с табл. 13.1
  РП. Базовые адреса всех 106 периферий совпадают с макросами `*_BASE` заголовка и с картой памяти
  РП (табл. 8.2, с. 70–72).

### 12. Доступ к полям статуса HASH.SR (не исправлялось)

- **Где:** строки 12182–12192.
- **Что:** поля `DCIS` и `DINIS` помечены `write-only`. По РП (с. 787) это флаги, которые выставляет
  аппаратура и сбрасывает программа (в том числе записью нуля). Их нужно читать, а в PAC для них
  нет метода чтения. В самом РП в таблице регистра SR эти биты подписаны `DCIE` и `DINIE`, как
  одноимённые биты регистра IMR, хотя по описанию это биты статуса.
- **Почему не исправлено:** сплошная сверка доступа всех полей с РП не проводилась, поэтому одно
  место выборочно не исправлялось.

### 13. Число блоков CAPCOM у TMR4–TMR15 (не исправлялось)

- **Что:** все 15 таймеров TMR1–TMR15 описаны в SVD как производные от TMR0 (`derivedFrom="TMR0"`)
  и наследуют массив `CAPCOM[0..3]`. По РП (с. 220): «В TMR0-TMR3 присутствуют четыре идентичных блока
  захвата/сравнения CAPCOM. В TMR4-TMR15 имеется по одному блоку захвата/сравнения CAPCOM».
  В PAC у TMR4–TMR15 доступны `capcom(1..3)`, которых в этих таймерах нет.
- **Почему не исправлено:** нужно отдельное описание таймеров TMR4–TMR15 вместо наследования. Это
  меняет структуру SVD и API PAC и выходит за рамки работы. Структура `TMR_TypeDef` в заголовке SDK
  тоже общая для всех таймеров.

### 14. Значения сброса HASH.SR и MSC.U_ITEM (не исправлялось)

- **HASH.SR**, строка 12163: в SVD `<resetValue>0x1</resetValue>`, в РП (с. 787) «Сброс: 0000_0000h».
- **MSC.U_ITEM[%s]**: в SVD значение сброса 0 для всех элементов, в РП (с. 699) «Сброс: 400h * i»,
  то есть у каждой записи своё значение. Одно значение `resetValue` для элементов массива SVD
  такое не выражает.
- **Почему не исправлено:** для HASH.SR источники расходятся; это можно проверить чтением регистра
  на плате после сброса, такая проверка не проводилась. Для MSC.U_ITEM разные значения сброса
  потребовали бы описать элементы массива отдельными регистрами; это не делалось.

### 15. Значение «Магма» поля CRYPTO.CONTROL.ALGORITHM (исправлено)

- **Где:** строки 12454–12475, поле `ALGORITHM` регистра `CRYPTO.CONTROL`.
- **Что:** в перечислении три значения: 0 — `AES_128`, 1 — `AES_256`, 3 — `Kuznechik`. Значения 2 нет.
- **Сверка:** по РП модуль CRYPTO реализует алгоритмы AES-128, AES-256, «Кузнечик» и «Магма» (с. 324),
  а поле `ALGORITHM` принимает значения 00 — AES_128, 01 — AES_256, 10 — MAGMA, 11 — KUZNECHIK (с. 337;
  то же в таблице регистра CONTROL, с. 794–795).
  В заголовке `K1921VG1T.h` того же SDK значение `CRYPTO_CONTROL_ALGORITHM_Magma = 0x2` есть (с описанием
  «GCM payload phase», не относящимся к этому полю).
- **Исправление:** добавлено значение `Magma` = 2 с описанием «GOST 34.12-2018 cipher with 64 bit block
  (Magma)» — так оно записано в SVD нового SDK производителя (см. раздел ниже).
- **Влияние на PAC:** без этого значения записать в поле 2 («Магма») можно было только небезопасным
  методом `bits()`, а `variant()` при чтении возвращал `Option`. После исправления у поля есть метод
  `magma()` и безопасный метод `set()`, а `variant()` возвращает значение без `Option`.
  Прошивки примеров от этого не изменились: проверено сравнением образов.

## Как проверялось

1. **Необходимость правок группы А.** Для каждого из 8 классов собирался SVD, где откатан только этот
   класс. Затем запускался svd2rust, а если он проходил — `cargo check` сгенерированного крейта.
   Результаты приведены в сводной таблице.
2. **Структурная проверка исправленного SVD** (скриптом): перекрытие полей, выход поля за ширину
   регистра, значение сброса вне полей, повторяющиеся имена, перекрытие регистров, выход за
   `addressBlock`, перекрытие адресов периферий, повторы номеров прерываний, шаг массивов. Оставшиеся
   срабатывания: 298 адресов, по которым расположено несколько регистров (с учётом массивов и
   производных периферий), — все объявлены через `<alternateRegister>`, в FLASHM и FLASHD цепочкой из
   четырёх регистров; и выход регистра `+0x40` блоков DAC0 и DAC1 за `addressBlock` (п. 10).
3. **Сверка с заголовком SDK** `platform/Device/K1921VG1T/Include/K1921VG1T.h`: базовые адреса,
   номера прерываний, перечисление CRYPTO.CONTROL.ALGORITHM (п. 15).
4. **Сверка с РП** — п. 6, 7, 9–15, а также таблица прерываний 13.1 и карта памяти 8.2 целиком.
   Значения в п. 2, 3, 4 и 8 (число 4, имя `VALUE`, ширина 32, имя `CTRL`) выбраны автором и с РП
   не сверялись.

## Ограничения

Исправленный SVD принимается svd2rust и согласован с РП и заголовком SDK в проверенных местах.
Правки проверены генерацией, компиляцией и сверкой с документацией; на плате они специально не
проверялись. Проверка файла по XSD-схеме CMSIS-SVD не выполнялась. Полная сверка всех регистров и полей с РП не
проводилась. Имена-заглушки `VALUE` (п. 3) в РП отсутствуют. Дефекты 10, 12–14 и прерывание
`L2_ERROR` оставлены как есть и описаны выше.

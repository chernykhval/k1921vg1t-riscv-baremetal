# Отчёт: правка SVD-файла К1921ВГ1Т для генерации Rust-PAC

## Что это и зачем

**SVD** — машинное описание чипа (XML): все блоки периферии, их адреса, регистры, биты.
Из него генерируют код доступа к железу. Тот же файл использовался для C-заголовка
`K1921VG1T.h`. Мы хотим сгенерировать из него **Rust-PAC** инструментом `svd2rust`.

Проблема: инструмент `svd2rust` **строгий** — он проверяет SVD на корректность и отказывается
работать при ошибках. А наш SVD (`k1921vg1t_sdk/tools/svd/K1921VG1T.svd`) оказался **сырым**:
он сделан на основе шаблона от ARM-чипов НИИЭТ (серия ВК) и содержит множество дефектов.
Пришлось их исправить.

**Важно:** мы правим **копию** — `projects/k1921vg1t-pac/K1921VG1T.svd`. Оригинал в SDK не тронут.

**Итог:** исправлено **8 классов дефектов** (суммарно ~48 отдельных мест). После этого
`svd2rust` проходит без ошибок и генерирует PAC.

## Подробно по каждой правке

### Правка 1 — Порядок байт (endian)
- **Где нашли:** строка 24.
- **Было:** `<endian>Endian.LITTLE</endian>`
- **Стало:** `<endian>little</endian>`  (сейчас — строка 24)
- **Что это:** тег указывает порядок байт (little-endian — младший байт первым).
- **Почему ошибка:** значение `Endian.LITTLE` — это «сырой» вывод какого-то Python-инструмента
  (repr перечисления), а стандарт SVD требует просто `little`. Явный след того, что файл
  генерировали автоматически и не проверяли.

### Правка 2 — Пустой тег nvicPrioBits
- **Где нашли:** строка 27 (в блоке `<cpu>`).
- **Было:** `<nvicPrioBits />`  (пустой самозакрывающийся тег)
- **Стало:** `<nvicPrioBits>4</nvicPrioBits>`  (сейчас — строка 28)
- **Что это:** `nvicPrioBits` — число битов приоритета прерываний в контроллере **NVIC**.
  NVIC — это **ARM**-контроллер прерываний; у RISC-V его нет вообще.
- **Почему ошибка:** тег унаследован от ARM-шаблона. Парсер `svd2rust` требует, чтобы он был
  и содержал число. Сначала попробовали удалить — парсер пожаловался, что тега нет; вернули
  со значением `4` (типовое). Значение ни на что не влияет (мы генерим под RISC-V), но должно
  присутствовать.

### Правка 3 — Регистры без имени (30 мест)
- **Где нашли:** строки 3880, 3909, 5320, 5652, 5702, 5731, 10703, 10746, 12207, 12259 и др.
  (всего 30) — в блоках GPIO (`MASKLB`/`MASKHB`), CAN, ADC, Hash и др.
- **Было:** `<name />`  (пустое имя)
- **Стало:** `<name>VALUE</name>`
- **Что это:** это регистры внутри «кластеров»-массивов. Имя массива несёт сам кластер,
  а у внутреннего регистра имя оставили пустым.
- **Почему ошибка:** в Rust у каждого регистра должно быть имя (иначе непонятно, как его
  назвать в коде). Дали всем заглушку `VALUE`. На нужные нам регистры (RCU, GPIO) не влияет —
  это экзотические регистры, которыми мы пользоваться не будем.

### Правка 4 — Нулевой размер регистра (8 мест)
- **Где нашли:** строки 6232, 16217, 17560, 21511, 25305, 26456, 32374, 33719.
- **Было:** `<size>0</size>`
- **Стало:** `<size>32</size>`
- **Что это:** `size` — ширина регистра в битах.
- **Почему ошибка:** регистр не может быть шириной 0 бит (тем более что у этих регистров есть
  поля до 16-го бита и reset-значения). Явная опечатка. На этом чипе регистры 32-битные —
  поставили 32.

### Правка 5 — Мусорный префикс в имени (2 места)
- **Где нашли:** строки 10540 и 10683.
- **Было:** `<name>&lt;&gt;TACC0</name>` и `<name>&lt;&gt;Reserved</name>`
  (`&lt;&gt;` — это экранированные символы `<>`, то есть имена буквально `<>TACC0`, `<>Reserved`)
- **Стало:** `<name>TACC0</name>`, `<name>Reserved</name>`
- **Что это:** имена регистров.
- **Почему ошибка:** символы `<>` недопустимы в имени переменной ни в Rust, ни в C.
  Откуда взялся префикс — неясно (артефакт генерации). Убрали его.

### Правка 6 — Противоречие «доступа» между регистром и полями (4 места)
- **Где нашли:** `SCVAL` в ADC (строка 9926), `SR` в HASH (строка 12162),
  `NODESTEST` (~строка 21121), `VALUE` (~строка 38118).
- **Было:** у регистра `<access>write-only</access>` (только запись),
  а у полей внутри — `<access>read-only</access>` (только чтение).
- **Стало:** у регистра `<access>read-write</access>` (и чтение, и запись).
- **Что это:** «доступ» говорит, можно ли регистр/поле читать и/или писать.
- **Почему ошибка:** нельзя пометить весь регистр «только запись», а его поле — «только
  чтение»: это логическое противоречие. Судя по смыслу (например, `SR` — статусный регистр,
  его читают), правильный доступ — «чтение и запись». Нашли все такие места скриптом, не по
  одному.

### Правка 7 — Неверный шаг массива CAPCOM  ✅ СВЕРЕНО С РП
- **Где нашли:** строка 33606 (кластер `CAPCOM[%s]` в таймере TMR0).
- **Было:** `<dimIncrement>12</dimIncrement>`  (шаг массива 12 байт)
- **Стало:** `<dimIncrement>16</dimIncrement>`  (сейчас — строка 33606)
- **Что это:** `CAPCOM` — массив из 4 одинаковых блоков; `dimIncrement` — расстояние между
  соседними блоками в байтах.
- **Почему ошибка:** каждый блок содержит 4 регистра по 4 байта (`CTRL`, `VAL0`, `VAL1`,
  `Reserved`) = 16 байт. Но шаг стоял 12 — соседние блоки массива налезали бы друг на друга.
  Раз есть явный `Reserved` на смещении 0xC, блок задуман 16-байтным. Поставили шаг 16.
- **ПРОВЕРКА:** сверено с руководством пользователя чипа `UM_K1921VG1T_10YA`, стр. 673,
  раздел «A.10 Регистры 32-разрядного таймера TMR». Смещения блоков: CAPCOM0 = +100h,
  CAPCOM1 = +110h, CAPCOM2 = +120h, CAPCOM3 = +130h → шаг ровно **16 байт (0x10)**.
  Фикс подтверждён документом.

### Правка 8 — Кластер и регистр с одинаковым именем (ADC.ACTL)
- **Где нашли:** строка 10415 (кластер `ACTL[%s]` в блоке ADC, внутри регистр `ACTL`).
- **Было:** кластер `<name>ACTL[%s]</name>` содержит регистр `<name>ACTL</name>`.
- **Стало:** внутренний регистр переименован → `<name>CTRL</name>`.
- **Что это:** кластер — массив блоков, внутри один регистр управления АЦП.
- **Почему ошибка:** имена кластера и его регистра совпали. svd2rust сгенерировал тип `Actl`,
  содержащий поле типа `Actl` — то есть **тип, содержащий сам себя** (бесконечный размер).
- **Особенность:** этот дефект `svd2rust` НЕ поймал — файл сгенерировался. Ошибку выдал уже
  компилятор Rust на этапе `cargo build` (`recursive type has infinite size`). То есть
  корректность проверяется на ДВУХ уровнях: svd2rust (структура SVD) и rustc (валидность кода).

## ВАЖНО: «генерируется» ≠ «100% верно»

`svd2rust` теперь отрабатывает без ошибок — это значит, что SVD стал **синтаксически
корректным и непротиворечивым**. НО это **не гарантирует**, что каждый регистр точно
соответствует железу. Часть наших правок — **обоснованные догадки**:
- `size 0 → 32` — почти наверняка верно (все регистры чипа 32-битные);
- `access → read-write` — верно по смыслу, максимум «избыточно разрешает»;
- `dimIncrement 12 → 16` — сверено с РП (UM, стр. 673), подтверждено;
- имена-заглушки `VALUE` — работают, но это не настоящие имена из документации.

**Что проверено надёжно:** адреса RCU (`0x50004000`) и GPIO (`0x40002000`) — по ним уже
мигали светодиоды из C, значит эти (важные для нас) части SVD **верны**.

**Итог по сомнительным («додуманным») правкам:**
- правка 4 (size 0→32, 8× регистр `Reserved`) — **безопасна**: в SVD адреса регистров заданы
  явным `addressOffset`, поэтому размер одного регистра не сдвигает другие. К тому же
  «Reserved» — заполнители/резерв, которыми мы не пользуемся.
- правка 6 (access→read-write, 4×) — низкий риск, максимум «избыточно разрешает».
- правка 7 (CAPCOM шаг 16) — **сверена с РП (стр. 673), подтверждена.**

Вывод: после проверки пропатченная часть SVD либо безопасна по построению, либо подтверждена
документом. Полная построчная сверка всего файла (тысячи регистров) не проводилась и не нужна:
риск сосредоточен в местах наших правок, а они разобраны.

## Почему это важно для отчёта DEVBOARDS

Это конкретное, измеримое подтверждение главного тезиса проекта: **готовой Rust-поддержки для
К1921ВГ1Т нет, а официальный SVD сырой** (унаследован от ARM-линейки ВК, 8 классов дефектов).
Прежде чем получить PAC, SVD пришлось чинить — это и есть часть работы, которую документируем.
